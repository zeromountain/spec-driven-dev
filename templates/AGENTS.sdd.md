## Spec-Driven Development

이 프로젝트는 `sdd` 플러그인으로 Spec-Driven Development(SDD)를 적용한다. 명세가 소스 오브
트루스이며, 구현 코드를 직접 고치는 대신 명세를 고치고 코드를 다시 생성한다.

### 역할

세 페이즈(spec → implement → review)마다 역할이 나뉘고 각자 쓰기 범위가 제한된다.
하드 게이트(`enforce: true`)가 켜져 있으면 **페이즈 경계**는 훅이 강제한다.

**spec** — Spec Architect 하나뿐이다(조사부터 작성, 스스로 적대적 재검토까지,
`specs/`에만 쓴다). 별도의 조사·감사 역할은 없다.

**implement** — Implementation Planner(AC 분해·영향 파일 확정, `tasks.md`만) →
Software Engineer(구현과 AC별 테스트를 함께, `src/`·`tests/`).

**review** (셋 다 쓰기 없음) — Code Reviewer(가독성·복잡도) · Security Reviewer(입력
검증·인가·시크릿·인젝션) · Performance Reviewer(N+1·복잡도·경계 없는 로딩).
**하나라도 `changes-requested`를 내면 기능은 완료가 아니다.** 판정을 평균 내지 않는다.
**명세 준수·AC 커버리지를 전담 판정하는 역할은 없다** — Code Reviewer가 review 단계의
유일한 기본값이다.

### 깊이

작은 변경까지 6개 역할을 다 돌리지 않는다. `sdd.py depth`가 인수 기준 개수·검증 경고·
본문 키워드를 근거로 `light`(역할 3개)와 `deep`(역할 4개)을 정한다. 보안·성능 리뷰어는
깊이와 무관하게 해당 신호가 잡히면 그 위에 붙는다(최대 6개) — 한 줄짜리 인증 수정에도
보안 신호가 있으면 리뷰가 돈다. `/sdd:run <설명> --deep`, `--light`로 직접 지정할 수 있다.

### 명세 구조

각 기능 명세(`specs/<slug>/spec-v<N>.md`)는 필수 8개 섹션을 모두 포함한다: 목적, 배경,
비즈니스 규칙, 기능 요구사항, 비기능 요구사항, 인수 기준(`AC-1`부터), 오류 케이스
(`EC-1`부터), 범위 밖. 권장 섹션 `입력과 출력`·`인터페이스`는 없으면 경고가 뜬다.
기능이 커지면 상위 명세 아래 컴포넌트 명세로 쪼개고 프론트매터에 `parent: <상위 슬러그>`를 적는다.

### 프로젝트 지식

명세보다 위에 있는 지식은 `docs/sdd/`에 둔다 — `prd.md`(제품 목표·사용자·MVP 경계),
`architecture.md`(구조·패턴·데이터 흐름), `adr/`(결정과 그 이유). 모든 에이전트가 명세보다
먼저 이 문서를 읽는다. 머릿속에만 있는 관례는 에이전트가 매번 추측하게 되니 여기에 적는다.

새 명세는 `sdd.py new`가 템플릿에서 만들어 주며, 안에는 `{{...}}` 플레이스홀더가 들어
있다. **하나라도 남아 있으면 검증에 실패하고 구현 단계로 넘어갈 수 없다.**

리뷰가 승인되면 남은 체크박스가 모두 채워지고 명세 디렉터리가 `specs/archive/<slug>/`로
옮겨진다. 손으로 체크하거나 옮기지 않는다 — 같은 기능을 다시 열면 제자리로 돌아오고
버전이 이어진다.

전체 규칙(프론트매터·ID 형식·검증 에러 목록·버저닝)은 `sdd` 플러그인의
`skills/spec-driven-dev/references/spec-format.md`가 정본이다.

### 진행 방식

`/sdd:run <기능 설명>`이 기본 경로다. 명세→구현→리뷰가 한 번의 요청으로 끝까지 돌아가며,
단계 전환·재시도·페이즈 게이트 조작은 `sdd.py`의 상태머신이 처리한다. 진행 위치는
`.sdd/state.json`의 `pipeline` 레코드에 있으므로, 세션이 끊겨도 `/sdd:run`을 인자 없이
다시 부르면 같은 자리에서 이어진다.

멈추는 경우는 세 가지다: 명세가 완성돼 **사람의 승인**을 기다릴 때(기본 켜짐 —
`.sdd/config.json`의 `humanGates`, 구현 계획 승인은 `plan: true`로 켠다), 명세 단계에서
물어야 할 미결 질문이 생겼을 때, 재시도 상한에 걸렸을 때(기본 단계별 2회). 승인은
에이전트가 대신하지 않는다 — 고칠 점을 말하면 같은 명세에 반영되어 다시 돌아온다.
확인 없이 끝까지 돌리려면 `/sdd:run <설명> --no-gate`.

### 회고와 학습 규칙

리뷰가 승인되면 회고 단계로 간다. 스크립트가 센 사실(명세·테스트·리뷰에서 되돌아간 횟수와
이유)이 `specs/archive/<slug>/retro-v<N>.md`에 남고, 사람이 고른 교훈만
`docs/sdd/learnings.md`에 `LRN-N`으로 쌓인다. 쌓인 교훈은 다음 기능부터 모든 에이전트의
컨텍스트에 실린다 — 같은 실수를 두 번 하지 않게 하는 장치다. 여러 기능에 걸쳐 반복되는
교훈은 이 AGENTS.md로 옮긴다.

### 여러 기능을 동시에

`/sdd:run`은 다른 기능이면 막지 않는다 — 기능마다 파이프라인이 하나씩 생긴다.
`/sdd:board`가 전체 현황을, `/sdd:run --all`이 전부를 배치 루프로 돌린다. 하드 게이트가
켜져 있으면 같은 페이즈끼리만 동시에 돌고, 구현 단계는 파일이 겹치면 직렬화된다.

**워크트리**를 켜면(`worktrees: true`) 기능마다 `.sdd/worktrees/<슬러그>/`에 독립된
체크아웃과 `sdd/<슬러그>` 브랜치가 생겨 두 제약이 모두 사라진다. 코드·테스트는 반드시
`workdir` 안에서만 쓴다 — 명세와 `.sdd/` 상태는 본체에 남는다. 승인돼도 브랜치는 자동
병합하지 않는다. 워크트리는 **나중에도 붙일 수 있다**: `/sdd:worktree add <슬러그>`
(진행 중인 파이프라인도 다음 단계부터 그 안에서 돈다).

### 명령

`/sdd:run` · `/sdd:board` · `/sdd:worktree` · `/sdd:spec` · `/sdd:implement` · `/sdd:review` · `/sdd:status` · `/sdd:phase`.
`/sdd:spec`·`/sdd:implement`·`/sdd:review`는 파이프라인을 한 스텝만 진행시키는 수동 경로다.
자세한 사용법은 `sdd` 플러그인의 `spec-driven-dev` 스킬을 참고한다.
