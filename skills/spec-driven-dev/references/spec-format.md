# 명세 형식 (정본)

명세 구조·ID 규칙·버저닝의 **단일 출처**다. `specs/README.md`와
`templates/AGENTS.sdd.md`는 이 문서의 요약만 담고, 상세는 여기를 가리킨다.

## 프론트매터

```yaml
---
feature: <슬러그>       # 부모 디렉터리 이름과 일치해야 한다
version: <N>            # 파일명 spec-v<N>.md 의 N 과 일치해야 한다
status: draft           # draft | approved | done | superseded
createdAt: <ISO8601>
---
```

`feature`/`version`/`status`가 없으면 에러. `validate`에 파일 경로가 주어지면
`version`↔파일명, `feature`↔디렉터리를 교차 검증한다 — 복사·붙여넣기로 버전이 어긋난
명세를 잡아낸다. `status`는 리뷰가 `approved`를 낼 때 `sdd.py advance`가 `done`으로 올린다
(오케스트레이터가 손으로 고치지 않는다 — `pipeline.md`의 "페이즈 게이트와의 관계" 참조).
같은 시점에 남은 체크박스가 채워지고 디렉터리가 아카이브로 옮겨진다 (아래 "완료와 아카이브").

## 8개 섹션

`validate`가 아래 8개 `## ` 헤더의 존재를 확인한다. 순서는 강제하지 않지만
`templates/spec.md`의 순서를 권장한다.

목적 · 배경 · 비즈니스 규칙 · 기능 요구사항 · 비기능 요구사항 · 인수 기준 ·
오류 케이스 · 범위 밖

같은 헤더가 두 번 나오면 에러다 — 뒤의 것이 앞의 것을 덮어써 조용히 누락되기 때문이다.
**펜스 코드 블록(``` 또는 ~~~) 안의 `##`는 섹션으로 세지 않는다**, 그래서 명세가 마크다운
형식 자체를 예시로 담아도 안전하다.

## ID 규칙

| 섹션 | 형식 | 비고 |
|---|---|---|
| 인수 기준 | `- [ ] **AC-<N>**: <조건 문장>` | 체크박스 **있음** |
| 오류 케이스 | `- **EC-<N>**: <상황과 기대 동작>` | 체크박스 **없음** |

- `N`은 1부터 연속. 중복·건너뜀은 에러. ID 없는 항목도 에러.
- AC 문장에 조건 표현(`~하면`, `~해야 한다`, `~안 된다` 등)이 없으면 **경고**.
- AC 문장에 모호 표현(빠르게·적절히·안전하게·잘·효율적으로·필요시·등등)이 있으면 **경고**.
  "빠르게 응답해야 한다"가 아니라 "1초 이내에 응답해야 한다"로 쓴다.
- 모호성은 경고에 그친다(에러 아님) — 휴리스틱이 틀렸을 때 검사기를 우회하는 문장을
  쓰게 만드는 것보다, 사람이 보고 판단하게 두는 편이 낫다.

## 플레이스홀더

템플릿의 미기입 표시는 `{{...}}`다. **하나라도 남아 있으면 에러**이며, 따라서
`sdd.py new`가 방금 만든 파일은 반드시 `valid: false`다. 이것이 "명세 없이 구현하지
않는다"를 실제로 강제하는 장치다 — 플레이스홀더가 남은 채로는 `implement` 페이즈로
넘어갈 수 없다.

펜스 코드 블록 안의 `{{...}}`는 예시로 보고 미기입으로 세지 않는다.

## 검증 결과

```json
{"valid": true, "errors": [], "warnings": [],
 "acIds": ["AC-1", "AC-2"], "ecIds": ["EC-1"]}
```

`errors`가 하나라도 있으면 `valid: false`. `implement` 전환은 대상 명세가
`valid: true`일 때만 허용된다. `--spec`을 생략하면 `state.activeSpec`으로 폴백하고,
그마저 없으면 차단된다 — 검증을 건너뛰는 경로는 없다.

## 버저닝

- 경로: `specs/<slug>/spec-v<N>.md`
- `sdd.py new "<설명>"`은 같은 슬러그에서 가장 큰 `N`을 찾아 `N+1`로 만든다.
  슬러그는 설명에서 자동 생성되며, 한글도 허용된다(NFC로 정규화). ASCII 슬러그를 쓰려면
  `--slug user-login`처럼 직접 지정한다.
- **동작이 바뀌면 새 버전.** 오탈자·표현 명확화처럼 동작에 영향 없는 변경만 제자리에서
  고친다. 애매하면 새 버전이 안전하다 — 버전은 되돌릴 수 있지만 "몰래 바뀐 동작"은
  추적이 안 된다.
- 리뷰 리포트는 `.sdd/reviews/<slug>-v<N>-<seq>.md`로 특정 버전에 붙는다.

## 완료와 아카이브

리뷰가 승인되면 `advance`가 한 창 안에서 세 가지를 한다.

1. 명세와 `tasks.md`에 남은 `- [ ]`를 전부 `- [x]`로 채운다. **이미 있는 체크박스만**
   바꾼다 — 오류 케이스는 체크박스 없는 불릿이고, 거기 체크박스가 붙으면 EC로 인정되지
   않아 검증이 깨진다. 코드 펜스 안의 예시와 프론트매터는 건드리지 않는다. 최신 버전만
   대상이다 — 지난 `spec-v<N-1>.md`는 그때 무엇을 요구했는지의 기록이다.
2. `status: done`.
3. `specs/<slug>/`를 **디렉터리째** `specs/archive/<slug>/`로 옮긴다. 평탄화하지 않는
   이유는 위의 `feature`↔디렉터리 교차 검증 때문이다.

`[x]`도 AC로 파싱되므로 체크된 명세의 `validate`·`trace`·깊이 판정 결과는 그대로다.

같은 기능을 다시 열면(`run`, `run --from`, `sdd.py new`) 아카이브에서 **자동으로
되돌아온다.** 버전은 이어지므로 `spec-v1.md`를 덮지 않고 `spec-v2.md`가 만들어진다.
`archive`는 예약된 슬러그다.

`validate`와 `trace`는 경로를 인자로 받고 파일이 없으면 그대로 죽는다. 옛 경로를 손으로
넣지 말고 `next`가 준 컨텍스트의 `specPath`를 그대로 쓴다.

## tasks.md

`specs/<slug>/tasks.md`는 명세 하나당 하나다(전역 파일 아님). implement 페이즈에서
`specs/` 안 유일한 쓰기 허용 경로다.

**직접 작성하지 않는다** — `sdd.py tasks <slug>`가 명세의 AC를 읽어 대응표가 채워진
상태로 만들어 준다. Engineer는 남은 `{{...}}`를 채우고 진행 상황을 체크한다. 승인 시점에
남은 체크박스는 `advance`가 마저 채우므로, 손으로 전부 체크하고 넘어갈 필요는 없다.
