# 명세 형식

## 8개 섹션

`validate` 서브커맨드가 아래 8개 `## ` 헤더가 모두 존재하는지 확인한다. 순서는 강제하지
않지만 `templates/spec.md`의 순서를 따르는 것을 권장한다.

1. 목적
2. 배경
3. 비즈니스 규칙
4. 기능 요구사항
5. 비기능 요구사항
6. 인수 기준
7. 오류 케이스
8. 범위 밖

## 인수 기준(AC) 형식

`## 인수 기준` 아래 각 항목은 다음 형식이어야 한다:

```
- [ ] **AC-<N>**: <검증 가능한 조건 문장>
```

- `N`은 1부터 시작해 연속으로 매긴다. 중복·건너뜀은 에러.
- ID가 없는 체크박스 항목은 에러.
- 문장에 "~해야 한다" 류의 조건 표현이 없으면 경고("빠르게 동작해야 한다"보다
  "1초 이내에 응답해야 한다").

## 검증 결과

`sdd.py validate <spec-path>`는 다음을 출력한다:

```json
{"valid": true, "errors": [], "warnings": [], "acIds": ["AC-1", "AC-2"]}
```

`errors`가 하나라도 있으면 `valid: false`. `implement` 페이즈로의 전환은 활성 명세가
`valid: true`일 때만 허용된다(`sdd.py phase implement --spec <slug>`).

## 버저닝

- 경로: `specs/<slug>/spec-v<N>.md`
- `sdd.py new <설명>`은 같은 슬러그 디렉터리에서 가장 큰 `N`을 찾아 `N+1`로 새 파일을 만든다.
- **동작이 바뀌면 새 버전을 만든다.** 오탈자 수정, 표현 명확화처럼 동작에 영향 없는 변경만
  기존 버전 파일을 제자리에서 고친다. 이 구분이 애매하면 새 버전을 만드는 쪽이 안전하다 —
  버전은 되돌릴 수 있지만 "몰래 바뀐 동작"은 추적이 안 된다.
- 리뷰 리포트는 `.sdd/reviews/<slug>-v<N>-<seq>.md`로 특정 버전에 붙는다.

## tasks.md

`specs/<slug>/tasks.md`는 명세 하나당 하나다(전역 파일 아님). implement 페이즈의
페이즈 게이트에서 `specs/` 안 유일한 쓰기 허용 경로다. Software Engineer가 인수 기준을
작업 단위로 쪼개고 진행 상황을 체크한다. 형식은 `templates/tasks.md` 참고.
